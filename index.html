In this assignment I decided to do some research on animation file formats. which lead me to the BioVision Hierarchy (.bvh) file format. The BVH format largely is used for recording motion capturing information and porting over to various media. I believe it's used sometimes in robotics to define movement in complex structures as well. Here is a good overview of the format I used while designing my loader, although it is not fully correct (or rather up to date).

Controls and some things to try:

  • Rotate the scene with your mouse and move with WS + the arrow keys.
  • Control the animation with the inputs below the frame.
  • Try turning off interpolation at low speeds to see frame jumps.

Where are these animations from?

The BVH files I'm using in this demo are from the open source Bandai-Namco-Research-Motiondataset repository on github. Additionally you can read the related paper "Motion Capture Dataset for Practical Use of AI-based Motion Editing and Stylization" Kobayashi et al. (2023).

So how do you parse BVH files?

Overall the BVH format is plain ASCII text and consists of two sections, a definition of joint points and a set of animation frames.

Joints

The joint or HIEARCHY section consists of nested joint definitions which define various properties:

  • The type of joint (ROOT or JOINT) and its name which follows the type. The next joint properties and children joints are defined within a pair of braces. There can also be multiple ROOT joints in a single bvh file allowing for multiple skeletons, but I ignored this in my parser.
  • The positions of joints in the OFFSET field which is in X, Y, Z order
  • The properties animation frames will later change, CHANNELS. Note that these channels can be in any order and this is the order the transformations should be applied. I believe it is convention for position channels to be first and then rotation, but this doesn't seem to be required. Additionally rotation channels are conventionally in YXZ order but do not even have to be consistent within a model, joints may all have different rotation orders... This was quite a headache as I did not realize the channels would deviate from YXZ so things were quite wonky looking at first.
  • End Site nodes label the end of a joint branch and only contain an OFFSET

Below is a small snippet from the walk.bvh file. Notice how we create the shape of the skeleton's lower body and begin the spine with multiple children joints branching off of the Hips joint. 

HIERARCHY
ROOT joint_Root
{
  OFFSET 0 0 0
  CHANNELS 6 Xposition Yposition Zposition Zrotation Xrotation Yrotation
  JOINT Hips
  {
    OFFSET 0 93.9241 -3
    CHANNELS 6 Xposition Yposition Zposition Zrotation Xrotation Yrotation
    JOINT Spine
    {
      OFFSET 15.7357 0 0
      CHANNELS 6 Xposition Yposition Zposition Zrotation Xrotation Yrotation
      JOINT Chest
      {
            ...
            End Site
            {
              OFFSET 0 0 0
            }
            ...
      }
    }
    JOINT UpperLeg_L
    {
      OFFSET -2.19248 -6.46944 0
      CHANNELS 6 Xposition Yposition Zposition Zrotation Xrotation Yrotation
      JOINT LowerLeg_L
      {
        ...
      }
    }
    JOINT UpperLeg_R
    {
      ...
    }
  }
}

Once we parse this information we can create a simple skeleton by making "bones" between the joints defined as seen below. The blue skeleton on may look malformed, but this is actually the starting position of the model in the HIERARCHY before any motion capture data is collected. On the other hand the green skeleton is in a more realistic pose, and to achieve this I've simply allowed it about one frame of animation (from the MOTION data we we look at next) to get it into place. Some BVH files will have a skeleton start in a realistic pose but this is not always the case as seen here.

Animation

After the HIERARCHY section there is the MOTION section which details the animation of the joints. First we have some metadata, the count of frames, and the duration of a frame in seconds. Next we have the actual animation information in the form of many lines of numbers. These numbers correspond directly to the CHANNELS we previously encountered on the joint definitions. The numbers are matched to a channel by order of occurrence if you were to traverse the joints depth first. The transformations themselves are meant to be done in the local space of the object, not the world space, so our shiny new hierarchical model setup is very suitable for running the animation data.

Conclusion / Notes

Now properly parse these two parts and you can load most BVH files. Overall, this format is relatively simple to parse since it is plain text like .obj files. Additionally braces are the only kind of grouping present and joint definitions are recursive so the parser itself ends up fairly simple. Some adjustments to a standard hierarchal model setup are needed to allow any order of rotations, but the changes aren't too large.

I don't believe I'll be using this in any future work since mapping actual geometry to the models would be complex but it was a interesting exercise regardless.
